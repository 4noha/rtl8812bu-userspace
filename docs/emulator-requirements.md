# 仮想チューナー（モニターだけのセットアップ）要件シート

最終更新: 2026-10-28

モニター（UN-15TD8D）を **チューナー無しで** 接続させるために、電波側が用意すべき
条件を、こちらの観測（読み取り専用）からまとめたもの。実装は送信側（別トラック）で行う。

観測手段: RTL8812BU + 本リポジトリの `rtl8812bu.monitor`。

---

## 1. モニターは何を探しているか

チューナーが居ない状態のモニターは、**WPS の Enrollee（登録したい側）** として
親機を探している。

| 項目 | 観測値 |
|---|---|
| プローブ間隔 | **約 8.2 秒**ごとに 1 回（1 回で「SSID 指定 + ワイルドカード」のペアを数組） |
| 2.4GHz | ch1 / ch6 / ch11 を探索（1 回あたり 3〜6 組と多い） |
| 5GHz | ch36 / ch40 / ch44 / ch48 を探索（1 回あたり 2 組程度） |
| 指定 SSID | チューナーの SSID（既知） |
| セキュリティ | WPA2（プローブには RSN IE を載せないのが通常） |

### プローブ要求の中身（バンドで変わる）

| 項目 | 2.4GHz | 5GHz |
|---|---|---|
| Supported Rates | 1, 2, 5.5, 6, 9, 11, 12, 18 Mbps（CCK を含む） | 6, 9, 12, 18, 24, 36, 48, 54 Mbps（OFDM のみ） |
| HT Capabilities (45) | 26 バイト | 26 バイト |
| WPS (221, `00:50:f2:04`) | 105 バイト | 105 バイト |

→ **ビーコン／プローブ応答もバンドに合ったレートを載せる**必要がある
（2.4GHz で OFDM のみ、5GHz で CCK を含む、は不整合になる）。

### WPS IE の中身（属性）

| 属性 | 値 | 意味 |
|---|---|---|
| 0x104a Version | 0x10 | WPS 1.0 |
| **0x103a Request Type** | **0x00** | **Enrollee（登録したい側）** |
| **0x1008 Config Methods** | **0x2288** | Display / PushButton / VirtualPBC / PhysicalPBC / VirtualDisplayPIN |
| 0x1047 UUID-E | 16 バイト（機器固有・非公開） | 個体識別 |
| 0x103c RF Bands | 0x03 | 2.4GHz + 5GHz の両方 |
| 0x1021 | 0x20 | （WPS 属性） |

→ 応答側は **Registrar** として振る舞い、PBC（ボタン方式）で進められる見込み。

## 2. 電波側が用意すべきもの

| # | 要件 | 根拠 |
|---|---|---|
| 1 | 対象 SSID のビーコンを出す（またはプローブ要求に応答する） | モニターは SSID を指定してプローブしている |
| 2 | 2.4GHz（1/6/11）または 5GHz（36/40/44/48）のいずれか | 両バンドを探索している。2.4GHz の方が本数が多く到達距離でも有利 |
| 3 | ビーコン/プローブ応答に **WPS IE** を載せる（Registrar として） | モニターは Enrollee。WPS で資格情報を受け取る想定 |
| 4 | WPS（EAP-WSC M1〜M8）を Registrar として話す | PBC / Display PIN を申告している |
| 5 | WPS で渡した PSK で 4-way が成立する | 接続後の暗号化 |
| 6 | バンドに合ったレートを広告する | 2.4GHz は CCK を含む / 5GHz は OFDM のみ |

### 期待される時間スケール

- モニターの探索は 8.2 秒周期。AP が同じチャネルに居れば **数秒〜十数秒で発見**される。
- ビーコン間隔は 100ms 程度が一般的（モニター側の受信は passive でも成立）。
- WPS の EAP-WSC は数秒で完了する想定（M1〜M8）。

## 3. こちらの観測で検証できること（送信なし）

エミュレータを動かしたとき、本リポジトリのアナライザで次を確認できる。

| 段階 | アナライザで見えるもの |
|---|---|
| 発見 | モニターのプローブが止み、**認証（auth）→ アソシエーション要求**が出る |
| WPS | EAPOL フレーム（EtherType 0x888e）の増加、4-way とは別の EAP シーケンス |
| 接続完了 | QoS Data / ARP / DHCP が見える（暗号化されるので中身は見えない） |
| 失敗の切り分け | アソシエーション拒否（status コード）、deauth の理由コード |

`--jsonl` 出力に `auth` / `assoc-req` / `deauth` の status が入るので、
**どの段階で落ちているか**を特定できる。

## 4. 未確認（送信が必要）

- プローブ応答に WPS IE を載せたとき、モニターが**即座に EAP-WSC を始めるか**
- WPS の PBC と Display PIN のどちらで進むか（モニターは両方申告）
- ビーコンのみ（プローブ応答なし）でも発見されるか
- 40MHz（倍速）設定時に、モニターが 40MHz で張るか

## 5. 実施結果（2026-10-28 夜・送信テスト 1 回目）

送信側の既存実装（AP + WPS Registrar、`ap_wps_full.py`）を **ch6（2.4GHz）で 180 秒**
動かしたときの観測。

| 項目 | 結果 |
|---|---|
| モニターのプローブ | **123 件**（180 秒、SSID 指定＋ワイルドカード） |
| 認証（auth） | **0 件** |
| アソシエーション要求 | **0 件** |
| EAPOL / EAP-WSC | **0 件** |

→ **モニターは AP を認識しなかった**（プローブを出し続けたまま）。
AP 側はプローブ応答を送る実装だが、モニターが次の段階に進まなかった。

### 仮説（次に確認する順）

1. **WPS IE の内容が足りない**
   実機チューナーの probe-resp は「長い版」の WPS IE（UUID・Panasonic の OUI・
   型番 `UN-TD8S` などを含む）を載せている（プロジェクト文書の観測）。
   こちらは短い版の可能性があり、モニターが「本物でない」と判断している。
2. **RSN / レート / WMM / DTIM の組み合わせ**
   2.4GHz の応答は CCK を含むレートが必要（モニターの 2.4GHz プローブは CCK 込み）。
3. **応答の送信条件**（レート・qsel・再送回数）。
   モニターは 8.2 秒ごとに数組しかプローブしないので、取りこぼすと次の周期まで待つ。
4. ビーコン側だけが届いていて、プローブ応答が届いていない可能性
   （1 台のアダプタでは自分の送信を観測できないため未確認）。

### 確認に必要なもの

**2 台目のアダプタ**（1 台で AP、もう 1 台でモニタ受信）があると、
「AP のビーコン/プローブ応答が正しく出ているか」を直接確認できる。
1 台の場合は、AP 側に送信フレームのダンプを仕込むのが最短。

## 6. 実機の WPS IE（7,266 個を集計して確定）

実機チューナーの捕捉から WPS IE を全数集計した結果。**フレーム種別ごとに構成が違う。**

### WPS 属性の正しい意味（重要な訂正）

| 属性 | 意味 | 長さ |
|---|---|---|
| 0x1044 | **WPS State** | **1** |
| 0x103B | **RF Bands**（0x01=2.4G / 0x02=5G / 0x03=両方） | **1** |
| 0x103C | **Response Type**（0x03=AP） | 1 |
| 0x1008 | Config Methods | 2 |
| 0x1041 | Selected Registrar | 1 |
| 0x1012 | Device Password ID（0x0004=PushButton） | 2 |

（以前この文書で 0x103B を「Response Type」と書いていたのは誤り。実機の probe-resp に
入っているのは RF Bands で、Response Type はビーコンの一形態にのみ現れる。）

### 実機の構成（出現数つき）

| フレーム | 属性数 | 構成 | 出現 |
|---|---:|---|---:|
| ビーコン（基本） | 3 | Version, State, VendorExt(6) | 6,209 |
| ビーコン（PBC 待ち） | 6 | + SelReg, DevPwdID=0004, 0x1053 | 935 |
| ビーコン（別形態） | 4 | Version, State, **ResponseType=03**, VendorExt | 84 |
| probe-resp（基本） | 12 | Version, State, **RFBands=03**, UUID-E, Manufacturer=`Panasonic`, Model=`UN-TD8S`, ModelNo=`0`, Serial=`0`, UUID-R, DeviceName=`UN-TD8S`, ConfigMethods=2108, VendorExt | 23 |
| probe-resp（PBC 待ち） | 15 | 上記 + SelReg, DevPwdID=0004, 0x1053 | 15 |

UUID-E（0x1047）は機器固有のため**公開しない**。AP は自分自身の固定値を持てばよい。

### 送信側で見つかった不具合（2026-10-28 修正）

| ファイル | 不具合 | 状態 |
|---|---|---|
| `ap_wps_full.py` | `0x1044` と `0x103B` を **2 バイト**で送っていた（仕様は 1 バイト）。Config Methods / Model No / Serial / UUID-R / Vendor Ext も欠落 | 修正済み |
| `ap_p2p.py` | 同じ 2 バイト誤り | 修正済み |
| `ap_wps_monitor.py` | 同じ 2 バイト誤り | 修正済み |
| `ap_wps_full.py` の UUID-E | モニターの UUID を流用していた（役割が逆） | AP 自身の固定値に変更 |

属性長が 1 バイト違うと、以降の属性がすべてずれて IE 全体が不正になる。
「プローブには応答するが認証に来ない」挙動と整合する。

## 7. 再試験の結果（2026-10-28 夜・2 回目）

WPS IE を実機準拠に直したうえで再試験した。

### 7-1. WPS 付き AP（ch6）

| 項目 | 結果 |
|---|---|
| ビーコン送信 | 1,094 |
| プローブ応答 | **107** |
| モニターのプローブ | 79 |
| auth / assoc / EAPOL | **0 / 0 / 0** |

→ IE の長さを直しても、モニターは認証に来なかった。

### 7-2. 既知の成功構成（クローン AP・`AP_IES=kira`・ch44）

10/27 にモニターが接続した実績のある構成でも、**150 秒間で auth 0 件**。

### ここから分かること

モニターは現在 **WPS の Enrollee（セットアップ）モード**にあり、
- WPS を提供しない AP には接続しない（7-2 が通らない理由）
- WPS を提供しても、こちらの offer を受け入れていない（7-1）

つまり「WPS の内容」だけでなく、**AP の送信がモニターに届いているか**を
確認できないと前に進めない。1 台のアダプタでは自分の送信を観測できないため、
次に必要なのは次のどちらか。

1. **2 台目のアダプタ**（1 台 AP / 1 台モニタ受信）で、ビーコンと probe-resp を直接検証
2. AP 側に**送信フレームのダンプ**を仕込み、ビーコン/probe-resp のバイト列を確認

## 8. 2 台目（ESP32-C3）で送信を観測した結果 ── 原因判明

1 台では「自分の送信が見えない」ため、ESP32-C3 を 2.4GHz の観測役にして
AP の送信内容を直接見た。

### 方法

- 8822BU で AP を ch6 に立てる（`ap_wpa2.py` / `ap_wps_full.py`）
- ESP32-C3（`tools/esp32-sniffer`）で管理フレームを受信
- ESP32 のチャネルを実行中に切り替えて 1/3/6/9/11 を巡回

### 結果

| チャネル | 近隣 AP の beacon | **私たちの AP** |
|---:|---:|---:|
| 1 | 122（IPC_331A, Buffalo） | **0** |
| 3 | 0 | **0** |
| 6 | 0 | **0** |
| 9 | 0 | **0** |
| 11 | 201（TP-Link） | **0** |

- ESP32 は**近隣 AP の beacon と probe-resp を正常に受信**している（スニファは健全）
- **私たちの AP の MAC（BSSID）を含むフレームは、どのチャネルでも 0 件**
- AP 側のログは `HW beacon downloaded (BCN_VALID=False)` ＝
  **ハードウェアがビーコンテンプレートを受け付けていない**
- AP の統計（bcn 1094 / probe 107）はソフト側の送信要求の数で、電波には出ていない

### 結論

モニターが認証に来ない理由は WPS IE の内容ではなく、**AP のフレームが電波に出ていない**こと。
ビーコンが出ていないので、モニターは AP を発見できない（プローブを出し続ける）。

### 次に直すべき点（送信側）

1. **ビーコンのハードウェア投入**（`BCN_VALID=False` の原因）
   - BCN_CTRL の設定順、ビーコン RAM への書き込み、BCN_VALID 待ち
2. ソフト送信（probe-resp / auth-resp）が電波に出ているかの確認
   - 送信レート・qsel・TX キューの設定
3. 上記が直れば、モニターの発見 → auth → assoc → WPS の順で進むはず

### この検証に使ったもの（再現手順）

```bash
# 1) ESP32-C3 にスニファを書き込む
cd tools/esp32-sniffer && pio run -t upload --upload-port /dev/cu.usbmodemXXXX
# 2) AP を立てる（別プロセス）
# 3) 観測（チャネルはシリアル経由で切替可能）
python3 tools/serial_sniff.py /dev/cu.usbmodemXXXX 30
```

## 9. 送信が出ないことの追い込み（ESP32 + 最小試験）

### 9-1. 最小の送信試験でも電波に出ない

`bcn_air_test.py`（30 発・1Mbps・ch6・自 SSID のみ）を実行し、ESP32 で ch6 を観測。

| 送信側の記録 | 値 |
|---|---|
| 送信 | 30 beacons / 3.0 秒 |
| BCN_CTRL | 0x18 |
| 実行後 BCN_VALID | 128 |
| 実行後 TXPKT_EMPTY | 0x07ff（全 TX キューが空） |

| 受信側（ESP32・ch6） | 結果 |
|---|---|
| 私たちの beacon | **0 件** |
| 近隣のフレーム | 226（action）＋ 4（probe-req） |

→ 送信側は「送った」と記録するが、**電波には出ていない**。
キューが空（0x07ff）なので、チップは受け取って処理している（エラーなし）。

### 9-2. AP でも同じ（HW ビーコン・ソフト送信の両方）

`ap_wps_full.py`（ch6・50 秒）で、AP は beacon 537・probe-resp 62 を記録。
同時に ESP32 で観測すると、モニターの probe-req は 22 件見えるのに、
**私たちの AP のフレームは 0 件**（beacon も probe-resp も）。

### 9-3. バンド依存の可能性

- 10/27 にモニターが接続できたのは **ch44（5GHz）**
- 今日の 2.4GHz（ch6）では、最小試験でも電波が出ていない
- 5GHz での再確認は、モニターが現在 2.4GHz を主に探索しているため未実施

→ **2.4GHz の送信（RF/BB の TX 設定・電力・パス）に問題がある可能性が高い**。
5GHz でだけ動いていた、という説明がつく。

### 9-4. 次に確認するレジスタ（送信側）

1. **TX パス**（どの RF パスで送るか）。アンテナは path A 側なので、
   TX が path B になっていると電波が出ない。
2. **2.4GHz の TX 電力**（電力インデックスが 0 になっていないか）。
   5GHz では 0xC20/0xE20 を書かない分岐があり、2.4GHz 側の扱いが逆になっている可能性。
3. **TX キューの投入**（OWN ビット／ページの割り当て）。`TXPKT_EMPTY=0x07ff` は
   「常に空」なので、投入に失敗している（送って消費された）可能性も残る。

### 9-5. 検証手段（準備済み）

`tools/esp32-sniffer` + `tools/serial_sniff.py` で、**修正のたびに 2.4GHz の
実電波をその場で確認**できる。beacon が出れば SSID と BSSID が表示される。

## 10. 参照（Linux + hostapd）の AP 開始列を捕捉して差分を取った

VM の Linux で `hostapd` を AP モードで動かし、**AP 開始時に何を書くか**を usbmon で
捕捉した（`/tmp/hapd.bin`、26 秒）。

### 参照が AP 開始時にやっていること（抜粋・16 進）

```
14.96 W 0x05a8 <- 0x01
14.96 W 0x0204 <- 0x87cc          ← ビーコンページ + BCN_VALID
14.97 W 0x0101 <- 0x07            ← REG_CR 上位バイト（AP モード）
14.97 BULK OUT 256B               ← beacon 本体（48B ヘッダ + 208B、SSID を含む）
14.97 W 0x0204 <- 0x87cc
14.97 W 0x0101 <- 0x06
14.98 BULK OUT 156B               ← probe-resp テンプレート
15.00 W 0x0500 <- 0x002f3226      ← EDCA VO
15.01 W 0x0504 <- 0x005e4328      ← EDCA VI
15.02 W 0x0508 <- 0x0000a42b      ← EDCA BE
15.03 W 0x050c <- 0x0000a44f      ← EDCA BK
14.99 W 0x0420 <- 0x00701f80      ← FWHW_TXQ_CTRL
15.04 W 0x0608 <- 0xf410400e
15.04 BULK OUT 74B                ← H2C
15.26/15.28 BULK OUT 150B ×2      ← probe-resp（SSID を含む）
```

### こちらの実装との差分

| 項目 | 参照 | こちら |
|---|---|---|
| beacon のバルク転送 | あり（256B） | あり（同等） |
| probe-resp テンプレートの投入 | あり（156B/150B） | **なし**（ソフトで応答） |
| **EDCA 下位バイト**（0x0500/04/08/0c） | あり（0x26/0x28/0x2b/0x4f） | **なし**（TXOP 側だけ書いていた） |
| FWHW_TXQ_CTRL（0x0420） | 0x00701f80 | 一部のみ |

EDCA の ECWmin/ECWmax/AIFS が無いと MAC がバックオフできず、送信が一切出ない可能性が高い。

### 試したこと（結果）

- 上記の EDCA 書き込みを `mac_init_bu.py`（初期化）に入れた → **初期化が失敗し
  CR=0xeaeaeaea（0xEA 状態）**。チップはプロセス終了後に復帰する。
- したがって**初期化ではなく AP 開始時**（参照と同じタイミング）に書く必要がある。

### 次の手順

1. `ap_wpa2.py` / `ap_wps_full.py` の AP 開始処理（`hw_beacon` の直前）に
   EDCA 4 本と 0x0420 を追加
2. C3 で beacon が出るか確認（`python3 tools/serial_sniff.py /dev/cu.usbmodem11201 15`）
3. 出れば probe-resp テンプレート（156B/150B）の投入も検討

## 11. 現在の状態（2026-10-28 深夜・引き継ぎ）

## 解決した最大のバグ: 2 回目の FW ダウンロードが全ゼロだった

初期化列では FW ダウンロードが **2 回** 現れる（probe 相当と start 相当）。
ページ番号を通し番号で振っていたため、2 回目の送信位置がリセットされず、
**40 ページすべて 0x00 を送っていた**。`0x0080` への `0x0001` 書き込みを
ダウンロード開始の合図として表に記録し（`('dl', ...)`）、そこで送信位置を
リセットするよう修正した。

- 修正前: `MCUFW_CTRL=0x00604078`（bit15 が立たない）
- 修正後: `MCUFW_CTRL=0x0000c078`（**FW 起動**）

教訓: 「バイト列が一致している」ことを確かめたのは 1 回目のダウンロードだけだった。
同じ処理が複数回現れる捕捉では、**各回を独立に検証する**こと。

期待するログ:

```
[init] 再生完了: ... MCUFW_CTRL=0xc078 fw_ready=True
[monitor] モニタモードへ切替: ... fw_ready=True
[chan] ch6 (2.4GHz) 155 writes
  0.123 beacon       len=... bssid=... ssid='...'
```

フレームが出ない場合の切り分け:

| 症状 | 見るところ |
|---|---|
| `urbs: 0` | RX が有効になっていない（モニタ切替の再生位置） |
| `urbs > 0` だが `frames: 0` | 前置きの解釈（長さの位置・`MAX_FRAME_LEN`） |
| `frames > 0` だが表示が変 | `ieee80211.parse()` |

## 未確定として残しているもの

- 読み出し値の不一致が 95〜177 件残る（`0x0204`, `0x1208`, `0x0030` の efuse 系）。
  いずれも FW 起動には影響していない。efuse の読み出し値は「読む順番に依存する
  ストリーム」なので、こちらの方が読み出し回数・順序の差でずれるのは想定内。
- RX 前置き 56 バイトのうち、長さ以外のフィールドの意味（RSSI 等）。
  相関が取れるまで**推測で名前を付けない**。
- チップが固着する条件。初期化の途中で失敗すると `0x04e0` への書き込みが
  タイムアウトする状態になり、USB の再列挙では戻らない（**物理的な抜き差し**が要る）。

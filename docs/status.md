## 途中で見つけたバグ（記録）

### 1. 2 回目の FW ダウンロードが全ゼロ

初期化列には FW ダウンロードが 2 回（probe 相当 / start 相当）現れる。
ページ番号を通し番号で振っていたため、2 回目は送信位置がリセットされず
**40 ページすべて 0x00 を送っていた**。`0x0080 <- 0x0001` をダウンロード開始の
合図として表に記録（`('dl', ...)`）し、そこで送信位置をリセットして解決。

- 修正前 `MCUFW_CTRL=0x00604078`（bit15 が立たない） → 修正後 `0x0000c078`

**教訓**: 「捕捉とバイト一致」を確認したのは 1 回目のダウンロードだけだった。
同じ処理が複数回現れる捕捉では、各回を独立に検証する。

### 2. モニタモード切替の捕捉が途中で切れていた

最初の捕捉は 3 秒窓で、モニタ起動の書き込みが 3.0 秒ちょうどで終わっていた
（＝窓の外に続きがある）。書き込みが途切れるまで待つ 20 秒窓で取り直したところ、
書き込みは 1,683 → 3,648 件に増え、受信が動くようになった。

**教訓**: 捕捉は「書き込みが止まったこと」を確認してから終える。
`docs/capture.md` の手順に反映済み。

### 3. 80 バイトの H2C を FW ページと誤認

FW ページの判定を「48 バイト以上」で行っていたため、80 バイトの H2C 転送
（`[0:2]` が偶然ペイロード長と一致）を FW ページとして扱っていた。
`[2:4] == 0x0030` も条件に加えて分離し、H2C は `('bulk', ...)` として
そのまま再生するようにした。

## 固着の調査（2026-10-28）

### 分かったこと

1. **`0x04e0` は保護付き書き込みのミラー**。観測は
   `R <reg> -> old / W 0x04e0 <- old / W <reg> <- new / W 0x04e0 <- new`。
   捕捉時の `old` をそのまま書いていたため、実機の状態が違うとミラーが食い違う。
   → `GuardedWriter` で「ミラーは実機の現在値、書き込む値は捕捉した絶対値」に修正。
   （この修正前後で挙動が変わり、差分適用にすると必要なビットが落ちて初期化が失敗することも確認）
2. **実際に落ちるのは毎回同じ 1 点**: モニタ切替の 61 書き込み目、
   `0x0020 <- 0xed`。ここでチップが無応答になる（読み書きともタイムアウト）。
3. その直前は `w13: 0x0002 <- 0x1c`（MCU 停止）→ `w35: 0x0020 <- 0xc1`。
   `0x0020` はハードが自ら `0xe5` にしている値を `0xed`（bit3 追加）に上書きする箇所。

### 試して駄目だったこと

| 施策 | 結果 |
|---|---|
| 書き込み間隔を 1ms に（VM は約 1.4ms 空けている） | 4 セッション目で固着（改善せず） |
| `0x0020` の前に 50ms 待つ | 失敗点が `0x0020` から **`0x0005`（書き込み 40 番目）へ移動**。固着率は改善せず |
| `0x0020 <- 0xed` を省略 | 固着はしないが **受信 0 件**（RX に必要な時計設定だった） |
| FW 稼働中は初期化を省略（高速路） | 固着率は変わらず（後に実験扱いへ） |
| 読み出し照合を有効化 | 固着率は変わらず |

**重要な観測**: 待ちを入れると失敗点が別のレジスタへ移る（`0x0020` → `0x0005`）。
つまり特定のレジスタの問題ではなく、**「捕捉列を盲目的に再生する」こと自体が
タイミング依存で不安定**ということ。

### 現在の理解

### 決定的な証拠

ポーリングを有効にすると、**読み出しの 100 箇所（586 中）が期待値と一致しない**ことが
分かった。つまり「待てば揃う」のではなく、**そもそもチップの状態が捕捉時と違う**。
捕捉は「その個体がその履歴で辿った状態」であり、こちらは別の履歴（ファーム稼働中／
リセット直後）から同じ列を強制している。これが再現性の限界。

盲目的な再生は、**時計・リセット系のレジスタ**で状態依存の競合を起こす。
同じ値・同じ順序で書いても、チップ内部の遷移が完了している保証がないため、
数分の 1 の確率で固まる。Linux ドライバは各所で状態ビットをポーリングして
待つが、こちらは「捕捉した瞬間の値」を書くだけで待っていない。

### 検証結果のまとめ（すべて実機）

| 施策 | 8 セッション中の結果 |
|---|---|
| なし（素の再生） | 3〜4 セッションで固着 |
| 1ms 間隔 | 4 セッション目で固着 |
| 読み出し照合あり | 同程度 |
| 高速路（init 省略） | 同程度 |
| `0x0020` の書き込みを省略 | 固着しないが受信 0 件（不可） |
| `0x0020` の前に 50ms 待つ | 失敗点が移動（改善せず） |
| 読み出しを期待値まで待つ（ポーリング） | 1 セッション目で固着。**読み出し不一致が 100 箇所**あり、待っても一致しない＝状態自体が捕捉時と違う |

### 対策（現実的）

- 既定は **1 回の抜き差しにつき 1 セッション**。異常終了しても次の起動で
  `preflight` が検出して**何も書かずに止まる**（悪化を防ぐ）。
- 根本解決には、時計・リセット系の書き込み前に**状態ビットをポーリングする**
  実装（ドライバの条件分岐の再現）が必要。これは「観測の再生」から
  「小さなドライバ」への移行になる。

## 運用メモ（固着を避ける）

1. **1 回の抜き差しにつき 1 セッション**を目安にする。FW が動いている状態で初期化を
   やり直すと、まれに初期化の途中で固まる（読みも書きもタイムアウトし、USB の
   再列挙では戻らない）。
2. 終了は必ず停止シーケンス（実装済み）で行う。異常終了した場合は次の起動で
   `preflight` が「応答しません」と出して**何も書かずに止まる**。
3. 既定は **20MHz**。40MHz は実装済みだが凍結（受信量が約 2.6 倍で後始末が重い）。

## 現状の到達点（ファームウェア再生の限界を含む）

- 受信・解析は実用域（20MHz/40MHz、9 チャネル、1,098〜1,779 フレーム/10 秒）
- 初期化は「観測列の再生」のため、数セッションに 1 回固着する（7 施策を試して改善せず）
- **運用: 1 抜き差し = 1 セッション**。長い 1 セッション（60〜300 秒）は安定して完走する
- 恒久対策は「状態を読んで分岐する小さなドライバ」への移行（別プロジェクト規模）

## ブロッカー: ファームウェアが起動しない

実機（macOS）で `rtl8812bu.monitor` を実行すると、初期化列の再生自体は
最後まで通る（書き込みエラーなし）が、FW の起動完了ビットが立たない。

### 観測値

| レジスタ | Linux ドライバ（捕捉） | こちらの実装 |
|---|---|---|
| `MCUFW_CTRL` (0x0080) | `0x0060c078` | `0x00604078` |
| `0xfe58`（FW DL 状態と推定） | `0x80` | `0x00` |

差分はビット 15（`0x8000`）のみ。ビット 14（`0x4000`）と 21/22（`0x600000`）は一致。

### ここまでに否定した原因

| 仮説 | 検証 | 結果 |
|---|---|---|
| FW のバイト列が違う | 転送列を捕捉と全比較 | **一致**（ヘッダ・ページ分割・パディング込み） |
| FW 転送が速すぎる | 1 ページ 20 ms 間隔で再試行 | 変化なし |
| 制御転送が速すぎる | 1 書き込み 1 ms 間隔 | 変化なし |
| 起動コマンドの再送で起動する | `0x0001 → 0x61 → 0x79 → 0x4078` を再送 | 変化なし |
| MCU が無効のまま | `0x0002` を読む | `0x1f`（ビット 0 = 有効）で一致 |
| USB リセットで初期状態に戻る | `libusb.reset()` 後に `0x0080` を読む | 戻らない（`0x4078` のまま） |

### 残っている差分

1. **初期状態**: QEMU 経由で再列挙させた直後のチップは `0x0078`
   （Linux 捕捉の開始時と同じ）。そこから再生しても起動しない。
2. **読み出し値のわずかな不一致**: 一致する初期状態から再生した場合でも
   `0x0002`（ビット 0）、`0x0204`（ビット 15）、`0x1208` など十数件が一致しない。
3. **USB 上の順序**: 捕捉は「送信要求（S）」の順で並んでいる。Linux ドライバは
   バルク転送を**非同期に複数同時投入**するため、実際のバス上の到着順は
   記録順と一致しない可能性がある（制御転送と混ざる）。

## 次にやること（準備済み・実機の抜き差しが前提）

**同じ初期状態から、Linux ドライバと自前実装の USB トラフィックを取得して差分を取る。**
バイト列は一致しているので、残る差は「順序」か「同時投入数」のどちらかであり、
これを切り分けられるのはこの方法だけ。

```bash
# VM 側（デバイスを VM にパススルーした状態）
sudo modprobe -r rtw88_8822bu
# 1) Linux ドライバの捕捉（基準）
sudo python3 tools/umon.py /dev/usbmon1 /tmp/ref.bin 20 &
sudo modprobe rtw88_8822bu; sleep 4; sudo ip link set wlan0 up; sleep 8
sudo pkill -f umon.py

# 2) 自前実装の捕捉
sudo modprobe -r rtw88_8822bu; sleep 1
sudo python3 tools/umon.py /dev/usbmon1 /tmp/ours.bin 20 &
sudo python3 -m rtl8812bu.monitor --fw /lib/firmware/rtw88/rtw8822b_fw.bin --secs 1
sudo pkill -f umon.py

# 3) 差分（書き込み列だけを比較）
python3 tools/diff_trace.py /tmp/ref.bin /tmp/ours.bin
```

`tools/diff_trace.py` は未実装（この手順のために作る）。

## 注意: チップが固まる場合がある

初期化の途中で失敗すると、レジスタ書き込み（特に `0x04e0`）がタイムアウトする
状態になることがある。この状態は USB の再列挙では戻らず、**物理的な抜き差し**で
復旧する。実機で試すときは抜き差しできる状態で行うこと。
